# Intent: Full Milestone Execution

## Intent and Outcome

Make Full work converge on user-visible acceptance without weakening feature-level assurance. Agents should reuse sufficient authority, plan one current milestone end to end, give modern models cohesive multi-file work packages, parallelize independently mergeable enabling work when profitable, and reserve independent Review for protected contracts and final whole-change assurance.

## Acceptance

### A-AUTHORITY-REUSE

When approved authority already answers product, protected-contract, and effect-authorization questions, Full execution reuses it without repeating approach comparison, section-by-section approval, or written-authority confirmation. Only a real unresolved decision returns to the user, in one consolidated decision packet when possible.

### A-FEATURE-PACKAGE-TIERS

Full is the feature assurance level. Each internal work package is classified as routine inline, protected-contract, or isolated parallel execution. A low-risk package does not inherit an independent Review merely because its feature is Full.

### A-USER-MILESTONE

The current runtime frontier is a user-visible milestone. It names stable acceptance IDs, a public entry point, a terminal controlled L2/E2E scenario, observable success, consumed protected contracts, and later exclusions. Internal parsers, records, locks, and helpers are work packages rather than milestones unless they close a necessary shared contract.

### A-COHESIVE-PACKAGE

Planning chooses the largest cohesive boundary that one writer can implement, self-review, and prove with one package L1 while remaining deliberately serial or independently integrable. One package may span related source and test files and contains its own RED/GREEN iterations; file count and individual assertions do not create controller frontiers.

### A-BOUNDED-LOOKAHEAD

Planning inspects the complete path from public entry to observable result for the current milestone, clusters normally two to four work packages, and declares one to three execution rounds. It does not precompute later milestones or a feature-wide DAG.

### A-PARALLEL-ENABLING

Parallel execution may include independently mergeable enabling packages that are not independently user-visible. Parallel still requires frozen consumed interfaces, disjoint writes and mutable resources, independent package L1, no unsplit transaction, and material critical-path benefit.

### A-MILESTONE-EVIDENCE

Package L1 proves one cohesive package. Milestone L2 proves the integrated affected closure and exercises the real public entry point or controlled E2E. Repository-wide L3 remains finalization-only. Internal GREEN evidence cannot substitute for milestone acceptance.

### A-REVIEW-SCOPE

Review budgets bind to a protected contract identity or the final whole change, not a file, parser, task, frontier slug, migration, or agent role. Routine packages have no independent Review. Accepted correction remains inside the original Review unit and does not reset its budget.

### A-COMPATIBLE-MIGRATION

Legacy static plans and progressive-frontier runs may enter milestone execution only at a clean, identity-bound safe boundary. Authority and exact evidence are reused without relabeling. Active writers, patches, Review, finalization, and effects close under their original rules first.

## Hard Constraints

- Preserve Micro and Standard top-level routing behavior.
- Preserve native patch complete-set admission and zero partial integration.
- Preserve post-apply versus post-commit recovery semantics.
- Preserve state-bound evidence identities and honest scope claims.
- Preserve final L3, final whole-change Review, live-effect approval, and post-effect smoke.
- Keep `manifest.json` as the sole runtime entry point.
- Keep task cards as the sole package-specific worker authority.
- Do not require model behavioral evaluation for this implementation; executable contracts and live Skill loading are the completion evidence.

## Non-Goals

- Leave-Undo, automatic milestone abandonment, or round-triggered rollback.
- A scheduler extension, runtime classifier, numeric task-size score, or token/tool budget.
- A whole-feature static implementation DAG.
- Automatic migration of active runs.
- Rewriting product authority or historical evidence.
- Removing TDD, verification tiers, protected Review, or final Review.

## Protected Invariants

1. A public milestone cannot be completed by a stub, mock receipt, or internal-only test.
2. A package may be broad only while its behavior is cohesive and its ownership, resources, failure model, and L1 remain explicit.
3. Parallel work never splits one transaction or shares an unisolated mutable resource.
4. Review role renaming, frontier renaming, migration, or correction cannot create a new budget.
5. Lower-tier evidence never supports a broader completion claim.
6. Live or destructive effects remain deferred until final evidence and approval.

## Authorization

This change may edit Lite workflow skills, prompts, execution-contract tests, README, manifest classifications, and package documentation. It may not change extension lifecycle, provider behavior, settings, external repositories, or execute live/destructive effects.
